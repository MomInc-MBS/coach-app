# Server import and authority boundary

Migration 0019 adds owner/client-workout uniqueness, immutable import metadata and an append-only competitive decision log. Guest rows receive an automatic terminal not_eligible decision. Completed server and legacy rows begin pending; only an explicit accepted decision is rankable. Imported history is personal history, never authority for XP, combat, training, route progression or daily round limits. Personal history/achievements can include owned imports.

POST /api/workouts/import is absent unless WORKOUT_IMPORTS_ENABLED is exactly the string true. No production configuration enables it. The gate precedes database/auth/body access. Enabled tests enforce same origin, authenticated canonical target, strict minimal codec body and a server-recomputed fingerprint/key. The epoch-guarded D1 batch inserts workout, initial decision and metadata atomically; owner/client uniqueness makes concurrent exact requests converge. A changed payload conflicts. Response receipt fields come from persisted metadata.

The new migration was generated with Drizzle metadata. Its generated workout rebuild referenced nonexistent old columns, so the unapplied SQL uses additive column changes and whole trigger statements instead. A second generate reported no schema changes. Invalid legacy completion timestamps are preserved in the source workout and use zero only in their initial decision timestamp.

Rollout order: migrate both configured databases before epoch-aware workers, then validate the disabled endpoints and clients. Keep imports off until complete Chunk 3 acceptance and separate live-upload authorization. Once imports or retained deletion epochs exist, do not roll back to a worker that treats all workouts as authoritative or accepts unfenced deletions/writes. Additive tables can remain while disabling the route. Do not drop retained epochs/receipts as a rollback shortcut.

Account GET exposes a coherent data epoch and deletion evidence. DELETE targets an explicit expected epoch and keeps identity/epoch/receipt tombstones. An already-confirmed historical deletion returns alreadyDeleted plus deletedEpoch and current evidence; deleted:false means this response did not establish a new deletion. Newer data remains intact. Primary deletion and its durable remote reconciliation marker commit together. Remote acknowledgment is monotone and can clear only older/equal queued work. Two databases cannot be one transaction: remote deletion remains pending until acknowledged, and already-dispatched external mail/push cannot be recalled.

The account export includes owned import metadata, competitive decisions and retained deletion receipts. Account deletion does not touch the device guest source or local import ledger. Local explicit proof handling releases only the appropriate historical head before a fresh import decision.
